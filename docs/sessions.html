Sessions — the API dance

Written 2026-08-31, mid-refactor. The create, the playlist rung, the program rung and the audio rung are live (the program and audio rungs landed 2026-09-01), and the session page has the player: one deck, a transport, the show as a rundown — a slot's clip is made the first time it is played, then the mic, the bed and the record run to plan, and the next slot goes in when the record ends. Opening segment 2 while segment 1 is on air, all the post-production choreography, is deliberately out of scope here. Companion to api.html, the data model underneath.

In one breath

The browser is the state machine; the server is stateless functions. GET / is a form; posting it creates a session and lands the client on /sessions/:id. From there the client's whole job is a loop: fetch the snapshot, inspect it, call the one rung the frontier asks for, fold the response in, repeat. Every rung is idempotent and lock-guarded, so retries and second tabs are safe by construction — the sequencing knowledge lives in the client, and the server just enforces preconditions per call. No queue, no worker, no polling endpoint: the response of each rung is the product.

GET  /                                       the form: prompt + voice
POST /api/sessions                           → { sessionId }, client goes to /sessions/:id
GET  /api/sessions/:id                       the snapshot: the whole tree, status derived
POST /api/sessions/:id/segments/:num/playlist   rung: tracks land          (Claude ×2 + Spotify)
POST /api/sessions/:id/segments/:num/program    rung: all slots land       (Claude ×1, + one per record without a card)
POST /api/sessions/:id/segments/:num/slots/:seq/audio   rung: one clip     (ElevenLabs ×1)
GET  /api/sessions/:id/segments/:num/slots/:seq/audio   the clip bytes, immutable

1. The rules of the dance

  • Rungs, not a pipeline. Each POST does exactly one stage for exactly one thing and returns the produced document in the response. Nothing runs when nobody asks.
  • Idempotent. A rung whose product already exists returns the kept row instantly, no model call. Refreshing mid-production costs nothing.
  • One producer per session. Every rung takes the session row lock (for update nowait); a concurrent producer gets 409 "session is already producing" and simply tries again later.
  • Preconditions, not queues. A rung called before its input exists (program before playlist, audio before program) is 409 with why. That guardrail is for races and bugs — a well-behaved client never hits it, because it only calls what the frontier asks for.
  • Status is derived. The client never receives "you are at stage X" as authority; it receives the data and derives the same status the server would (the server's status field on the wire is a convenience, computed from presence the same way).

2. The form and the create built

GET / is the front desk: the ask (free text, ≤ 500 chars), who's on the mic (the roster from settings.voices, names and ids only, the pick remembered per browser), and the log — every session so far, newest first, each a row back to /sessions/:id as it stands. The roster and the log come with the page; the session page's title is the way back. Submitting the form:

POST /api/sessions
{ "prompt": "rainy sunday soul, nothing after 1979", "voiceId": "…" }

→ 200 { "sessionId": "8f14e45f-…" }        instant: no model call, no Spotify
→ 400 { "error": "…zod's why…" }

One transaction inserts the session and segment 1 at open — a session never exists without its first segment, so the client's loop has something to stand on immediately. The client navigates to /sessions/:id and everything after this is the loop.

3. GET /api/sessions/:id — the snapshot built, grows slots

The session as stored, whole: the ask, then every segment in order, each carrying whatever production has landed. It never produces anything and it is no-store while the document can still grow. Small on purpose — words, the writer's two numbers, the card's intro and refs, never audio and never the telemetry receipts (proposed, candidates, the raw program output stay in the database).

{
  "sessionId": "8f14e45f-…",
  "prompt": "rainy sunday soul, nothing after 1979",
  "voiceId": "…",
  "createdAt": "2026-08-31T17:02:11Z",
  "segments": [
    {
      "num": 1,
      "status": "programmed",              // derived: open | playlisted | programmed | voiced
      "rationale": "why this set answers the ask",
      "tracks":  [ { "id", "uri", "name", "artists", "album", "image", "durationMs", "pick", "why" }, … ],
      "dropped": [ "no hits for …", … ],
      "slots": [                            // absent columns are absent keys; [] until programmed
        { "seq": 1, "kind": "break",  "trackId": "…", "words": "…", "leadLine": "…",
          "voiced": true,  "clipKey": "sessions/8f14e45f-…/1/1.mp3",
          "clipMs": 40600, "bedInMs": 0, "leadMs": 6848 },
        { "seq": 2, "kind": "talkup", "trackId": "…", "words": "…", "voiced": false },
        { "seq": 3, "kind": "segue",  "trackId": "…", "voiced": true }   // no clipKey: done, silent
      ]
    },
    { "num": 2, "status": "open", "tracks": [], "slots": [] }
  ]
}

The frontier — how the client knows what to do

The client inspects, it is never told. Walk the segments; the frontier is the last segment plus the first unvoiced slot inside it, and each state maps to exactly one next call:

What the snapshot showsThe one next call
last segment openPOST …/segments/:num/playlist
last segment playlistedPOST …/segments/:num/program
last segment programmed, slot seq is the first with voiced: falsePOST …/segments/:num/slots/:seq/audio
last segment voicedout of scope here (this is where "open segment num + 1" will live)

This is what makes resume free: a page load on /sessions/:id re-fetches the snapshot, the same derivation lands in the same place, and the loop continues as if it never left. There is no client-side production state worth persisting — the snapshot is the state.

4. The playlist rung built

POST /api/sessions/:id/segments/:num/playlist
{ }                                          // optional partial Knobs, debugging pass-through

→ 200 { "num", "status": "playlisted", "rationale", "tracks": […], "dropped": […] }
→ 409 { "error": "session is already producing" }
→ 502 { "error": "only 3 tracks composed (need 4)", "dropped": […] }

Inside the request, under the session lock: Claude proposes records by name, Spotify search hydrates each into real candidates, Claude composes the playlist from those candidates by id — it cannot invent a track, every id is validated against the pool. The propose brief reads the ask before it names anything: a record the ask names is song 1 exactly as named, an artist it names opens with their record that best answers it, and a mood or a scene opens with the record that defines it — the canonical hit, the first thing heard. It proposes more than the playlist holds (six for four), so compose can drop a weak lead; the search drops a title's feat tag (searchQuery, pure) and keeps five hits per pick, so the single is on the table beside the remixes; compose is told the version matters and that the opener stays first. Two Claude calls and ~a dozen searches, tens of seconds; the response is the product. The client shows the ask and a producing state while it waits, then paints art and titles the moment this resolves — the first progressive-enhancement beat of the page.

5. The program rung built

POST /api/sessions/:id/segments/:num/program

→ 200 { "num", "status": "programmed", …segment doc with slots, none voiced }
→ 409 { "error": "session is already producing" }
→ 409 { "error": "segment has no playlist yet" }
→ 502 { "error": "…" }

One Claude call writes the whole segment — the break and every talk-up, sweeper and segue in one pass — because the writing is one coherent piece: the break sets up the set and the talk-ups reference what is around them. Looping Claude per slot would cost N round-trips for worse copy; the thing that actually gates playback is audio, and that lands per slot in the next rung. Under the lock: read the segment's tracks (absent → 409), the cards — the table first, the missing ones made now, all at once (a talk-up needs a card with a ≥ 7 s intro; a card that can't be made is logged and its slot can only be a segue) — one call at medium effort with every record and its card in the brief, validate against the clock rules, then insert every session_slot row in one transaction — kind, words, lead line, legal ID; the voice half all null. The legal ID is the server's, not the writer's: on segment 1 it is set from settings.station.identity and prepended by the audio rung (the hour turning between later segments is still to be decided). The body may carry { clockMs }, the browser's clock as ms since local midnight, so the DJ knows the listener's time. The raw output is kept on the segment as telemetry. The program half is immutable once written.

The client folds the slots in and the rundown gains its words — the second progressive beat: you can read the whole segment before you can hear any of it.

6. The audio rung built

POST /api/sessions/:id/segments/:num/slots/:seq/audio
     { "again": true }                                    optional: another take of a voiced slot

→ 200 { …the slot doc: "seq", "kind", "words"?, "voiced": true, "clipKey"?, "recordUnderMs"?, "voiceInMs"?, "introMs"? }
→ 409 { "error": "session is already producing" }
→ 409 { "error": "segment has no program yet" }

GET  /api/sessions/:id/segments/:num/slots/:seq/audio     → audio/mpeg, immutable, cache forever

POST produces, GET streams. The client doesn't probe GET to discover state: it POSTs (idempotent — a voiced slot returns its row with no TTS call), and fetches the GET endpoint only when the response has a clipKey. A voiced slot without a clipKey is a segue; there is nothing to fetch, just play the record.

Inside the POST: the slot's spoken text (legal ID, words, lead line, in that order) through ElevenLabs plain TTS in the session's voice, PUT to the bucket at sessions/<sessionId>/<num>/<seq>.mp3, then the row update (clip_key, voiced_at) in one statement. Bucket first, row second, so a stamped row without media can't exist; a crash in between leaves an unreferenced mp3 the retry overwrites. A segue voices instantly (nothing to say). A failed TTS is a 502 and the row is untouched; the client may try again. No timestamps, no alignment: the mix is the player's (the data model).

Another take. { "again": true } on a voiced slot with something said reads the same words once more with the roster as it stands now — the voice's model, speed, the lot — and lands it under a new key, sessions/<sessionId>/<num>/<seq>-<take>.mp3; the old bytes stay in the bucket, unreferenced. The GET is cached forever, so the player names the take in the clip's URL (?take=) and a new take is a new fetch. On the page it is the arrows beside a voiced row: the row spins while ElevenLabs works, and if that cue is in the deck the new take plays at once.

The player is the old station's, on the session page (app/(app)/sessions/[id]/): the desk (the lamp, who is connected, the request), the transport — art, three lines, the record's clock, ⏮ ⏯ ⏭ — and the show as a rundown, a row per slot on the amber rail. One deck (use-deck.ts) holds one cue at a time. Loading a cue makes its clip if it isn't yet (this POST), fetches it and reads its length, lays the plan from the kind, the length, the writer's two numbers and the card's intro (plan.ts, pure, tested), and runs three lanes from one clock — the mic is the voice <audio> element and the bed a looping buffer in one Web Audio graph, the bed's gain scheduled on the audio clock; the record is the Spotify device (this tab, Web Playback SDK, the listener's own Premium account through PKCE at /spotify/callback), started at its mark. The transport shows the cue — the three lanes, the record's lane running to its vocal where the card knows the intro, and the head sweeping across — then the record's own clock; the record is ducked under the voice — the device's volume stepped down as the voice comes in over it and back up once it is done, the only knob Spotify gives us — and both strips scrub (the mix runs again from the new head, the mic seeked into its clip and the bed's gain picked up mid-ramp; the record seeks in place). Play/pause is the transport's; which slot plays is the rows' (a tap) and ⏮ ⏭'s; when the record ends the next slot goes in on its own. Pause freezes everything; play again resumes the record when it alone is sounding, else the slot runs from the top (transport.ts, pure, tested). One tap does it all even when the tab isn't the device yet: the tap registers it and the cue runs when it's ready.

8. When a rung fails

FailureOn the wireClient's move
Concurrent producer (second tab, double click)409 session is already producingback off, re-fetch the snapshot later — whoever holds the lock is doing the same work
Called out of order409 with the missing preconditionre-fetch the snapshot; the frontier was stale
Production failed (model, Spotify, ElevenLabs)502 with the message and receiptsnothing landed (the transaction rolled back) — the same POST retries the whole rung, idempotency makes that safe
TTS failed inside the audio rung200 with a fallbacknothing — the slot is done, just humbler; the rundown shows the badge
Why no queue or worker. The sequencing knowledge ("playlist before program before audio") lives in the client's loop; the server enforces preconditions per call and locks per session. A queue would add infra that runs when nobody is listening, a place for state to live outside the database, and a polling protocol — for a pipeline whose every stage already fits in one request/response. The 409s are the entire coordination mechanism, and they are guardrails, not the happy path.
