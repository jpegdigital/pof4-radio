Sessions — the API dance

Rewritten 2026-09-04 for the slot-first show. Everything here is live: the create, the snapshot, the fill rung, the slot rung, the clip and the track, and the session page's loop that runs one slot ahead of the listener. Companion to domain.html, the data model underneath; the decisions that shaped it are in slot-first.md.

In one breath

The browser is the state machine; the server is stateless functions. GET / is a form; posting it creates a session and lands the client on /sessions/:id. From there the client's whole job is a loop: fetch the snapshot, ask the frontier for the one call it wants, make it, fold the response in, repeat. The show is one list of slots. A fill proposes a few more (one model call, a catalogue search per proposal); a slot rung writes one slot and voices it in the same request (one model call, one TTS call); the browser pulls the slot's track the moment the pick is known. Every rung is idempotent and lock-guarded, so retries and second tabs are safe by construction. No queue, no worker, no polling: the response of each rung is the product, and the first sound is two model calls away from the ask.

GET  /                                   the form: prompt + voice
POST /api/sessions                       → { sessionId }, client goes to /sessions/:id
GET  /api/sessions/:id                   the snapshot: the clock, every slot, status derived
POST /api/sessions/:id/fill              rung: a few more slots proposed     (Claude ×1–7 with catalog tools + Qobuz search)
POST /api/sessions/:id/slots/:seq        rung: one slot written and voiced   (Claude ×1 + ElevenLabs ×1)
GET  /api/sessions/:id/slots/:seq/clip   the clip's bytes, immutable
POST /api/sessions/:id/slots/:seq/track  pull the slot's pick                (Qobuz ×1, once ever per track)
GET  /api/sessions/:id/slots/:seq/track  the track's bytes, immutable

1. The rules of the dance

  • Rungs, not a pipeline. Each POST does exactly one stage for exactly one thing and returns the produced document in the response. Nothing runs when nobody asks.
  • Idempotent. A rung whose product already exists returns the kept rows instantly, no model call. Refreshing mid-production costs nothing.
  • One producer per session. The fill and the slot rungs take the session row lock (for update nowait); a concurrent producer gets 409 "session is already producing" and simply tries again later. The track pull is the exception: a track belongs to the library, not the session, and the browser pulls it while the slot rung holds the lock.
  • Preconditions, not queues. A slot asked for before it is proposed is 404 ("fill first"); a track asked for before its slot is written is 409. Guardrails for races and bugs — a well-behaved client never hits them, because it only calls what the frontier asks for.
  • The server decides what, the browser decides when. The browser sends a slot number and its clock; whether that slot is the break, whether the legal ID is due, which version plays and what is said are the server's, from the clock settings and the writer.
  • Status is derived. A slot is proposed until it has a pick, written until it is voiced, voiced after — from presence, never stored; the status field on the wire is computed the same way.

2. The form and the create built

GET / is the front desk: the ask (free text, ≤ 500 chars), who's on the mic (the roster from settings.voices, names and ids only, the pick remembered per browser), and the log — every session so far, newest first, each a row back to /sessions/:id with how many slots it holds. Submitting the form:

POST /api/sessions
{ "prompt": "rainy sunday soul, nothing after 1979", "voiceId": "…" }

→ 200 { "sessionId": "8f14e45f-…" }        instant: one row, no slot, no model call
→ 400 { "error": "…zod's why…" }

The client navigates to /sessions/:id and everything after this is the loop. Production starts with the first fill.

3. GET /api/sessions/:id — the snapshot built

The session as stored, whole: the ask, the clock (so the browser knows the low-water mark), then every slot in order, each carrying whatever its production has landed — the proposal; then the pick with its tags and whether the bucket holds it, the chart, the copy, the timing; then the clip key. It never produces anything and it is no-store while the document can still grow. Never on the wire: the hits (the browser has no use for them), the writer's thinking, the clock the write was made at, audio. A missing settings.clock row is a 500 naming it.

The frontier — how the client knows what to do

The client inspects, it is never told. nextMove(slots, clock, cueSeq, attempted) (loop.ts, pure, tested) gives the one call to make now, or none:

What the page holdsThe one next call
no slots at all, or the proposed ones are down to clock.lowWaterPOST …/fill (once per slot count)
else the first unvoiced slot f, when f.seq ≤ (cue's seq, or 0) + 1POST …/slots/f (once per slot, per page life)
elsenothing — wait for the deck; a cue change re-runs the loop

So before play only slot 1 is written; once slot k is in the deck, slot k+1 is written; the show never runs more than one voiced slot ahead of the listener and never spends a model call on a slot nobody will reach. A slot that comes back with a pick the bucket does not hold has its track pulled at once (POST …/track, not awaited) so it is in the bucket by the time it is up. Each move is made once per page life: a failure stays on screen, a reload retries. And resume is free: a page load re-fetches the snapshot, the same derivation lands in the same place, and the loop continues as if it never left.

4. The fill rung built

POST /api/sessions/:id/fill                      no body

→ 200 { "added": [ …SlotDoc, all "proposed" ], "dropped": [ "no hits for …", … ] }
→ 409 { "error": "session is already producing" }
→ 502 { "error": "no proposal found a version to play", "dropped": […] }

Under the session lock: every slot's title and artist go to the proposer — the written ones as played, the unwritten as coming up, never name any of these again — and one Claude call names clock.fill + 2 songs in play order, with the catalog in the room: two tools, search (Qobuz catalog/search, typed to albums, tracks, artists or playlists, or untyped for all four side by side) and album (album/get, a record's tracks in its order). The brief tells the proposer to look up anything it is not sure of — a record or a song it does not know, a release newer than it remembers — before naming it, and that a record named in the ask is the show in that record's order, every track, carried on by each fill from where the show stands; the SDK's tool runner loops the lookups (LOOKUPS at most; running out with no answer is a 502, never a guess) and the last message is the structured answer. A fresh show reads the ask first: a song it names is song 1 exactly as named, an artist it names opens with their song that best answers it, a mood or a scene opens with the song that defines it. A proposal already in the show (or twice in the same answer) is dropped, case-insensitive. Qobuz search finds up to three streamable versions of each (searchQuery strips the feat tag), in parallel; each proposal with at least one hit becomes a session_slot row — the proposal and its hits, nothing judged — in the proposer's order, seq continuing from the last, until clock.fill are added. One transaction. The rundown gains dim "coming up" rows the moment this resolves.

5. The slot rung built

POST /api/sessions/:id/slots/:seq
{ "clockMs": 31234567, "again": false }          clockMs: ms since the browser's local midnight, required

→ 200 { …SlotDoc, "status": "voiced" }
→ 404 { "error": "slot 7 is not proposed yet — fill first" }
→ 400 { "error": "…zod's why…" }
→ 409 { "error": "session is already producing" }
→ 502 { "error": "elevenlabs 401: …", "slot": { …SlotDoc, "status": "written" } }   the write is kept
→ 502 { "error": "…" }                                                                nothing landed

One request, under the lock, in order of precedence: no such slot → 404; voiced and not again → the kept row, no production; voiced with again and words → another take, the words untouched; written but not voiced (a voicing that failed) → the voice only; proposed → the write, then the voice.

The write

The clock says what this slot is: isBreak(seq, clock.breakEvery) — slot 1 and every breakEvery after (5 → 1, 6, 11…) — and, on a break, whether the legal ID is due: legalIdDue is true on slot 1 and whenever the hour of this clockMs differs from the hour of the last break's. The brief carries the ask, the clock as a time of day, the station and the DJ, this slot's proposal and its hits as a menu with lengths, the last three slots' copy, everything played, another DJ's chart of any of the hits from an earlier session (newest three, read-only), and — for a break only — the legal ID when due, the weather (NWS) and the headlines (Google News); a failed feed is logged and left out. Then one Claude call returns the whole slot (Written, shapes.ts): the pick (which hit plays, by id), the chart (the ramp before the first vocal and whether it is sure of it, where the vocal lands, how it ends, the feel), the copy (a kind — break, talk-up, sweeper, segue — the words, the break's lead line, why) and the timing (the two numbers the mix follows). A refusal or a pick outside the hits gets one more try; nothing usable twice and the slot is written as a segue on the first hit, no chart, the reason as its treatment — the show goes on.

The house rules (checkSlot, rules.ts, pure, tested) hold the answer to the clock: the clock's break is the break whatever the writer chose, a break anywhere else is a sweeper, a talk-up needs a ramp of 7 s or more the writer is sure of, a talk-up or sweeper with no words is a segue, the timing is clamped, the ramp and the outro are clamped to the pick's length, and the legal ID lands only on a break when due. Every step-down is kept on the slot as its fallback. One update lands every written column plus clock_ms and the writer's thinking (a receipt, never on the wire). The log says slot 2 written: sweeper, Fleetwood Mac — Rhiannon (LP Version) (2934757).

The voice

The slot's text (legal ID, words, lead line, in that order) through ElevenLabs in the session's voice, PUT to the bucket at sessions/<sessionId>/<seq>.mp3, then the row stamped (clip_key, voiced_at). Bucket first, row second, so a stamped row without media can't exist. A slot with nothing to say (a segue) is stamped voiced with no clip and no TTS call. No timestamps, no alignment: the mix is the player's. If the voicing fails after a write in the same request, the write is committed and the answer is 502 with the slot as written; the next request for it voices only, no second model call.

Another take. { "again": true } on a voiced slot with something said reads the same words once more with the roster as it stands now and lands it under a new key, sessions/<sessionId>/<seq>-<take>.mp3; the old bytes stay in the bucket, unreferenced. On the page it is the arrows beside a voiced row; if that cue is in the deck the new take plays at once.

6. The clip built

GET  /api/sessions/:id/slots/:seq/clip?take=<clipKey>    → audio/mpeg, immutable, cache forever
→ 404 { "error": "no such clip" }                                the slot has no clip (a segue, or not voiced)

The bytes, streamed from the bucket. A key is written once, so the answer is immutable; the browser names the take in the URL so another take is another fetch. The client never probes this to discover state — it reads clipKey off the slot document.

7. The track built

POST /api/sessions/:id/slots/:seq/track          no body, not under the lock

→ 200 { "held": true, "id", "title", "artists", "album", "image", "durationMs" }
→ 404 { "error": "unknown slot" }
→ 409 { "error": "slot 4 is not written yet" }
→ 502 { "error": "qobuz track/getFileUrl failed (401): …" }        the token rotated: paste a fresh one

GET  /api/sessions/:id/slots/:seq/track          → audio/mpeg, immutable, cache forever

The track is addressed through the slot that picked it — the slot is the proof the station wants this song, and the pull spends the listener's Qobuz account — but the row and the key are the library's: track.id is the Qobuz id, the bytes live at tracks/<id>.mp3, and every session after finds them. Inside the POST: a track row exists → held already, no Qobuz call. Else the bucket is asked (a signed HEAD): bytes with no row — a crash between a PUT and its insert, or the rows wiped — → the row is rebuilt from the pick's tags, no download. Else the pull: Qobuz MP3 320 (qobuz.ts: a signed track/getFileUrl on the listener's own token, then the CDN), PUT, then the row. Bucket first, row second, so a row always points at media; the tags on the row are Qobuz's own, copied from the picked hit, nothing judged.

Not under the session lock, on purpose: the browser fires this the moment a slot comes back with a pick, while the slot rung may still be voicing the next one; two pulls of the same track at once cost one duplicate download and land the same bytes under the same key (on conflict do nothing). Playback never touches Qobuz: the browser fetches the GET once as a blob (voice-cache.ts, the same cache as the clips), so scrubbing is instant and a replay is free.

What can go wrong is Qobuz's side and surfaces as a 502 with the API's own words: a 401 on every call means the token rotated (paste a fresh one from play.qobuz.com into 1Password, set it on radio-web); a 400 "Invalid Request Signature" means the web player's app pair rotated, and the code scrapes the new one on its own; a 30-second file where a track should be means the plan lapsed — download refuses samples rather than air one.

The player

One deck (use-deck.ts) holds one cue: a written or voiced slot. Loading it fetches the clip and the track side by side (a pull the page has not managed yet is made here — a retry of a failed one), reads the clip's length, lays the plan from the kind, the length, the writer's two numbers and the chart's ramp (plan.ts, pure, tested), and runs three lanes from one clock — the mic is the voice <audio> element, the bed a looping buffer and the track its MP3 in a second <audio> element through a gain node, all in one Web Audio graph, the bed's and the track's gain scheduled on the audio clock; the track starts at its mark and is ducked under the voice. Play/pause is the transport's; which slot plays is the rows' (a tap, once a row is voiced and held) and ⏮ ⏭'s; when the track ends the next slot goes in on its own if it is voiced — it was written while this one played, its track pulled the moment the pick was known — and the page says "loading the next slot" rather than going silent if it is not yet. The first tap unlocks the graph and both elements for iOS. In the background on iOS (Safari hidden, the screen locked) the graph keeps running because it was made under a "playback" audio session (navigator.audioSession, iOS 17.5+; any other type is interrupted on hide and silenced by the ringer switch); a hidden page's timers fire up to a second late, so each lane is seeked to the real head when its start fires (offsetsAt); a call taking the audio interrupts the context, and the deck holds — the head frozen, phase held — and plays again from there when it comes back (onContext); on return to the page the record's own clock is checked against the head and the mix laid again from the record if they came apart (realign), else the context is resumed by hand (WebKit does not always); and the lock screen is the Media Session (media-session.ts): the pick's title, artist, album and cover, and play, pause, ⏮ and ⏭ into the same transport, what it shows the transport's rule (lockScreen: loading between slots stays "playing", the scrubber only once the record is on). The three clocks — wall time for the head and the timers, the audio clock for the gains and the bed, the record's element for the record — are tied once at start; every rule for their coming apart is pure and tested in transport.ts.

9. When a rung fails

FailureOn the wireClient's move
Concurrent producer (second tab, double click)409 session is already producingthe move stays attempted; a reload re-fetches the snapshot — whoever holds the lock is doing the same work
A slot asked for before it is proposed; a track before its slot is written404 fill first / 409 not written yetre-fetch the snapshot; the frontier was stale
The fill found nothing playable; the writer failed outright502 with the message and receiptsnothing landed (the transaction rolled back) — the error stays on screen, a reload retries the whole rung; idempotency makes that safe
The writer gave nothing usable twice200: a segue on the first hit, no chart, the reason as treatmentnothing — the slot plays, silent; the rundown shows it
A rule stepped the kind down200 with a fallbacknothing — the slot is done, just humbler; the rundown shows the badge
Voicing failed after the write502 with slot.status = "written"fold the slot in; the next request for it voices only, no second model call
The pull failed502 from the track routethe row says "not held"; the deck pulls again when the slot is loaded, and the page pulls again on load
settings.clock missing500 / 502 naming the rowfill it on /settings; there is no default in code
Why no queue or worker. The sequencing knowledge ("fill when low, write one ahead of the cue") lives in the client's loop; the server enforces preconditions per call and locks per session. A queue would add infra that runs when nobody is listening, a place for state to live outside the database, and a polling protocol — for a pipeline whose every stage already fits in one request/response. The 409s are the entire coordination mechanism, and they are guardrails, not the happy path.
