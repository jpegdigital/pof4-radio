Radio — code architecture, graded

A read of the code as it stands at 09e56ad (main, 2026-09-20), domain by domain, graded against .claude/rules/coding-standards.md. A survey, not a plan: it names what is there and where it departs from the standard. Nothing here has been changed.

0. Method and rubric

What was read. Line by line: every file in src/lib/ except the prompt adapters' bodies, every route handler, every producer in api/sessions/ (pick, planning, headline-choice, write, fill, rules, shapes, generation, doc, params), the Qobuz client, scripts/prep.mts, the settings actions, the browser's types.ts. Outlined and grepped, not line-read: session-view.tsx, use-deck.ts, player.tsx, rundown.tsx, plan.ts, transport.ts, headlines.ts, weather.ts, prep-news.mts, prep-weather.mts, the editors, the tests. Grades on those are marked provisional. The import graph, the boundary touchpoints and the idiom counts are from grep over the tracked tree, tests excluded.

The rubric. Six criteria, each a clause of the coding standard. A cell is + meets it, ~ partly, − departs from it.

KeyCriterionClauseThe question asked of each domain
K1ContainmentV — colocation, single responsibilityHow many files speak to this boundary directly? One wire, or sprinkled?
K2InversionAcronyms — DI, IoC; V — explicit over implicitIs the collaborator handed in (config, client, fetchFn), or reached for inside the function (env(), pool(), claude())?
K3FailureIII; Error Handling StandardsA specific error type? A timeout on every external call? Anything swallowed or silently nulled?
K4Config as dataIV; VI — magic numbersAre the knobs named constants with one source, or literals in the logic?
K5Types at the edgeV — type safetyIs data crossing the boundary parsed (zod), or asserted (as T, query<T>)?
K6TestabilityII — mock the boundary, not the internalsIs the pure part table-tested? Can the boundary be replaced without vi.mock of modules?

Tags on findings. S1 structural: shapes how the code can change. S2 correctness risk: can produce a wrong or lost result. S3 hygiene. by design marks a departure that CLAUDE.md chooses on purpose; those are listed because the brief was to grade against the coding standard, and collected in §4 so they can be decided once rather than per finding.

Two processes, two wirings

The web process and the cron workers reach the same three boundaries through different code. The web side has the singletons and the zod'd env; the worker side builds its own. The plain-Node constraint (no @/ alias, no next) is why; the cost is that the better-defended pool is the worker's.

Per-domain notes

1. Jev. The reference shape in this repo. lib/jev.ts owns the wire (askJev: key, timeoutMs, fetchFn all handed in) and the law (readJev), with JevError carrying status. Each producer is three pure steps around one call: xRequest → askJev → readX, and the first and last are table-tested. The marks against it are small: PICK_MODEL = "jev-1.13.0" (pick.ts:6) duplicates the env default (env.ts:28); { apiKey, model } is assembled from env in two routes; planning.ts carries unnamed numbers (:33 5000, :81 8, :136 3000, :144 3); readChart narrows Jev's strings with as (:29, :40, :45) where the menu already constrains them.

2. Bucket. Bucket interface, createBucket(config), a singleton accessor on top; SigV4 is pure and tested against the AWS vectors. No timeout on any of the three verbs; failures are plain Error with the status in the message, so a caller cannot tell a 403 from a 500 without parsing text.

3. Env. One schema, required means required, the boot fails rather than the show. env() is a global accessor, and eleven files call it; where it is called from a route to build a config for something else (Jev, Qobuz) that is composition at the edge and fine, where it is called from inside a producer (write.ts:47, fill.ts:124) it is a hidden dependency (F5).

4. Pure law and shapes. isBreak, legalIdDue, checkSlot, statusOf, slotDoc, nextMove, the plan, the transport: pure, give/want tested, no I/O. Three definitions of the slot kind (rules.ts:5, shapes.ts:21 unused, browser types.ts:22); Hit, Chart, SlotKind, MixPlan are spread over doc, rules, planning so that those three import each other's types in a ring (F16). slotDoc is pure but trusts unparsed JSONB (F8).

5. Guard. One gate in proxy.ts, verification pure and tested. GUARD_OPEN = true (proxy.ts:17) is a feature flag as a code constant — standard IV says data; CLAUDE.md already says flip it back.

6. Prompts. Strict Handlebars, declared variables checked against the zod schema at compile, blank output rejected, preview CLI on the same path. The mark is direction: nine imports run from lib/prompts/ up into app/api/sessions/, and the input types of the two Claude producers are defined in the prompt adapters (F4).

7. Qobuz. A factory over a config, QobuzError with status and body, the bundle parser, the signature and the mappers pure and tested. No timeout on any of the four fetch calls (:299, :348, :352, :432 — the last one downloads a whole MP3). Responses are JSON.parse(body) as T (:304) against hand-written Raw* interfaces — the one un-owned API in the system is the one not parsed. The resolved app pair is cached on globalThis regardless of which cfg asked.

9. Prepared content. lib/prepared.ts is the best database boundary in the repo: the connection is handed in (Pool | PoolClient), rows are zod-parsed on read. Against it: the Dallas rule in three places with two different failure behaviours (F10); headlines.ts and weather.ts sit in api/sessions/ though no route imports them; dead surface (F14).

10. Settings. Shapes are pure and client-safe, loaders are server-only — the split is right and documented. Four loaders repeat one select (lib/settings.ts), a fifth copy is in prep.mts:54, the page reads the table a sixth way (settings/page.tsx:36), and the write lives in actions.ts:36. loadNews does not name its key on a malformed row; the other two do. Roster edits are read-modify-write with no lock (single operator; noted, not graded).

11. Claude calls. Three call sites, each with its own options: write.ts (messages.parse, max_tokens: 2048, 60 s), fill.ts (toolRunner, max_tokens: 16000, no timeout given), prep-news.mts (own client, 6500 and 3500). No error type: a Claude failure reaches the route as whatever the SDK threw. Output is zod-held on all three, which is the strong part.

12. Postgres. The pool is one file; the SQL is everywhere, which is the house rule. Graded on what the standard asks regardless: no timeouts on the web pool, rows typed by generic assertion, connection discipline left to each route (F6), and the rung's tests have to intercept SQL strings by text (pick-flow.test.ts:196).

13–16. See F7, F11, F2, F1.

3. Findings

S1 — structural

F1ElevenLabs is the one external service with no module S1

  • slots/[seq]/route.ts:452–466 and tts/preview/route.ts:18–29 each spell out the URL, output_format=mp3_44100_128, the three headers and the error string. Only ttsBody is shared (lib/voices.ts).
  • The rung's call has a 30 s timeout; the preview's has none.
  • Failure is new Error(`elevenlabs ${status}: …`) — no type, truncated at 200 in one and 300 in the other.
  • The voicing cannot be replaced in a test except by stubbing global fetch and matching on URL (pick-flow.test.ts:405).

Standard: V single responsibility; III specific error types; Error Handling — external calls MUST have timeouts. Two instances is under the WET threshold; the grade is for the missing timeout and the untyped error, and for being the odd one out next to lib/jev.ts.

F2The slot rung is one 545-line function at four levels of abstraction S1 by design

  • In one POST: HTTP parsing, the lock, 17 SQL statements, savepoint choreography, Jev orchestration, the writer, the TTS wire, the bucket put, stage timing, and four blocks of pure assembly.
  • The pure blocks have no test of their own: headline history from previous generations (:171–180), the SlotGeneration record (:270–294), the NewsReceipt (:343–383, 40 lines), the take record (:470–488). Standard I says extract "pure judgment worth table-testing"; these qualify.
  • Evidence of the cost: pick-flow.test.ts is 578 lines and needs eight vi.mock calls (db, prepared, bucket, env, settings, pick, planning, write), a global fetch stub, and a fake query that dispatches on SQL text. That is mocking internals, which II forbids, because there is no seam to mock at.
  • loadVoices() runs twice (:141, :444); env().ELEVENLABS_KEY is read at :132, 300 lines before its use; let w; at :326 is untyped.

Standard: SLAP; II mock the boundary; V one file, one sentence. CLAUDE.md asks for "a hot path stays one readable file" — see §4.

F4lib/prompts imports upward, and owns the producers' input types S1

  • Nine imports from lib/prompts/* into app/api/sessions/*: chart.ts:3, selection.ts:3, write.ts:5 (Hit from doc); mix.ts:3, write.ts:6 (MixPlan from planning); fill.ts:4 (Qobuz types); news.ts:3 (Article). Two are runtime values, not types: fill.ts:5 (numbered, Proposal) and write.ts:7 (Written) from shapes.
  • And back down: shapes.ts:1 imports lib/prompts/descriptions; planning.ts, pick.ts, write.ts, fill.ts import the registry. No runtime cycle today, by one leaf file.
  • WriteInput and FillInput are declared in lib/prompts/write.ts and lib/prompts/fill.ts and re-exported by the producers (write.ts:8, fill.ts:10). WriteInput is also what session_slot.generation.input stores forever (generation.ts:16). So a persisted record's shape is owned by a prompt-formatting module.

Standard: dependency inversion — the general layer (lib) depends on the specific one (app). CLAUDE.md describes lib/ as "app-level process concerns"; the prompt adapters are session-domain code that happens to live there.

S2 — correctness risk

F5Inversion is applied to Jev and Qobuz but not to Claude S2

  • producePick(input, { apiKey, model }), producePlan(…, config), chooseHeadlines(…, config), produceFill(q, input) with Qobuz handed in, readPreparedNews(db, …) with the connection handed in.
  • produceWrite(input) reaches for claude() and env().CLAUDE_MODEL (write.ts:47–48); produceFill takes Qobuz as an argument and then reaches for Claude the same way (fill.ts:122–124). Two styles inside one function signature.
  • Consequence: the Jev producers run under plain node in the eval scripts; the Claude producers cannot, which is why prep-news.mts builds its own client.

Standard: DI, IoC; V explicit over implicit.

F6The rung holds one connection and draws more from the same pool of five S2

  • route.ts:71 takes a client and keeps it to :543, across Jev, Claude and ElevenLabs (20–90 s). Inside that span loadClock/Identity/Voices/News (:138–143) and loadVoices (:444) go through pool(), i.e. other connections. The fill route does the same (:55–59).
  • max: 5 and no acquire timeout (db.ts:11): five producers in flight each hold one and wait for a second that never frees. The lock-free track route and the snapshot share the pool. Latent at one listener; GUARD_OPEN and "friends can test" is the scenario that reaches it.
  • The long transaction itself is the design (the row lock is the mutex) and is not the finding; the second draw is.

Standard: III fail fast — this fails by hanging.

F7No error taxonomy at the HTTP edge S2

  • 24 sites of err instanceof Error ? err.message : String(err) in the tree, 8 of them in the routes. Three error types exist (JevError, QobuzError, FillError); routes read FillError.dropped and QobuzError.body and nothing else. JevError.status is never read outside its test.
  • Status is by route, not by cause: a failed insert is 502 (sessions/route.ts:26); a missing settings.clock row is 500 from the snapshot and 502 from the rung and the fill; a zod failure on a stored roster is 502. 502 means "upstream failed"; the browser cannot tell "retry" from "fix /settings".
  • Three handlers have no try at all — clip/route.ts, news/route.ts, track GET — so a bucket or SQL failure there is Next's bare 500. In the snapshot the first query sits outside the try (:25).
  • Every catch is a catch-all (VI bans them by name); raw internal messages, SQL errors included, go to the client.

Standard: III specific types, catch only what you can handle; VI catch-all handlers.

F8Rows and JSONB are typed by assertion; old rows are read under new types S2

  • client.query<SlotRow>(…) is a cast. hits, generation, news, selection are JSONB and never parsed on read. doc.ts then casts again: :133 as Chart["outro"], :136, :142 as SlotKind, :147.
  • Everything is kept forever and the shapes are versioned in place ("prepared-1", "mix-5", "headlines-2", "script-2", "recording-1"), so the table holds several generations of shape under one TypeScript type. No reader branches on version.
  • Concrete exposure: doc.ts:138 and :150 read r.generation?.input.plan… — optional only at the first hop. A retained row whose generation predates input makes slotDoc throw, and slotDoc runs for every slot of every snapshot.
  • Contrast: lib/prepared.ts:134,152 parses on read; lib/settings.ts parses on read. Qobuz responses are the same pattern on the HTTP side (qobuz.ts:304).

Standard: V type safety — "strongest type system available" stops at the driver.

F9Copy validation is split, and one half loses the receipt S2

  • Word budgets, fixed words, empty copy: checkSlot (rules.ts:39). Publisher attribution: inside produceWrite (write.ts:62–64).
  • When checkSlot rejects, the route records the attempt and the rejected copy before rethrowing (route.ts:329–339 — "Preserve returned-but-rejected copy"). When the attribution check rejects, it throws before produceWrite returns, so there is no receipt to record: the billed call, its brief and its output are not retained. The stated invariant ("everything produced is kept") has a hole exactly where the writer misbehaves.

Standard: V single responsibility (one law, two homes); Audit Trail.

F10One rule, three copies, two behaviours S2

  • "Scheduled news supports Dallas, TX, America/Chicago only": headlines.ts:187 (filters local sources), lib/prepared.ts:119–125 (returns null — the break airs with no news and no log line), scripts/prep.mts:58–63 (throws with a message).
  • Third instance, so standard I says extract. The null is a silent failure by III: a control-room edit of the city turns the news off with nothing said anywhere.
  • Same file: usableNews (prepared.ts:97–102) requires revision and expiresAt in its types and reads neither.

Standard: I third instance; III silent failures forbidden; VI magic strings.

F11The browser has no API client, and its wire types are a hand copy S2

  • Nine fetch sites to the app's own API across four files (table in §2). The track POST is issued from session-view.tsx:99 and again from use-deck.ts:377, with different timeouts (90 s and none).
  • 7 browser sites of (await res.json().catch(() => null)) as T (home-desk:63, session-view:71, 101, 202, 221, 298, use-deck:378): a swallowed parse error followed by a cast. Four different ad hoc answer types (SlotAnswer, { added?, error? }, { held?, error? }, …).
  • types.ts re-declares Tags, Chart, SlotKind, SlotStatus, Clock, Slot by hand against doc.ts SlotDoc, rules.ts, lib/clock.ts. They already disagree: Slot.fallback is { from: string; to: string }, the server's is SlotKind. types.ts does import a type from @/lib/news, so type-only imports across the line are already accepted.

Standard: V colocation, type safety; III no swallowed errors.
