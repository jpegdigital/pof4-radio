Sessions — the data model

Read from the code on 2026-08-31, mid-refactor. session and session_segment are in the schema and live; session_slot joined them on 2026-09-01 with the program rung. Companion to sessions.html, which covers the API dance over this model.

In one breath

A session is one listening: the ask, verbatim, and the voice — nothing else. It owns segments, numbered from 1, each one sweep of the show: a DJ break and its songs. A segment is produced in rungs, each rung landing a column set whole — the playlist (tracks), then the program (slot rows: every word the DJ will say, one slot per track), then the voice (each slot's clip, one at a time). Status is never stored; it is derived from what is present. Everything produced is kept forever; nothing is re-made — except a clip, on request: another take of the same words, under a new key, the old one kept.

session ─┬─ session_segment (num 1) ─┬─ session_slot (seq 1)   ← the break
         │                           ├─ session_slot (seq 2)
         │                           └─ … one per track
         └─ session_segment (num 2) ─ …

1. session in schema

db/schema/session.sql. Created instantly by POST /api/sessions, in one transaction with segment 1 — a session never exists without its first segment. It never changes after creation (the updated_at trigger is there for hygiene, not workflow).

ColumnTypeWhat it is
iduuidPrimary key, generated.
prompttextThe listener's ask, verbatim. Every production rung reads it from here.
voice_idtextThe roster voice picked at creation. The whole session is voiced in it.
created_at, updated_attimestamptzBookkeeping.

The session row doubles as the production lock: every rung takes select … for update nowait on it, so at most one thing produces for a session at a time and a second producer gets a clean 409 instead of a duplicate model call.

Status is derived, never stored

A segment's stage falls out of which column sets are present. No status column, no state machine table — a crashed rung leaves nothing to repair, just an absent column set to produce again.

StatusDerivationThe client can…
openrow exists, tracks nullrequest the playlist
playlistedtracks present, no slot rowspaint art and titles; request the program
programmedslot rows present, some slot's voiced_at nullshow the rundown's words; request each slot's audio
voicedevery slot's voiced_at setplay the whole segment

Telemetry columns stay off the wire

proposed and candidates (and, once the program rung lands, a program jsonb holding the writer's raw output) are receipts: why the machine did what it did. They live in the database and never leave it — GET /api/sessions/:id returns rationale, tracks, dropped and the slots, not the receipts.

3. session_slot in schema

The slot is the unit of everything after the playlist: one track's introduction — how it is brought on air, every word said over it, and eventually the clip that says them. The program rung writes all of a segment's slots in one transaction from one Claude call (the writing is one coherent piece; the break sets up the set, the talk-ups reference what is around them). The audio rung then fills each slot's voice half one slot at a time, so slot 1's clip — the break — is playable while slots 2–N are still voicing.

The row

-- One track's introduction: written whole by the program rung, voiced one at a time.
create table session_slot (
  id           uuid primary key default gen_random_uuid(),
  segment_id   uuid not null references session_segment (id) on delete cascade,
  seq          integer not null,          -- 1-based, matches the track's position in tracks
  track_id     text not null,             -- the Spotify id of tracks[seq - 1]; belt and braces

  -- the program half, immutable once written
  kind         text not null,             -- break | talkup | sweeper | segue
  words        text,                      -- everything said; null for a segue
  lead_line    text,                      -- breaks: the one sentence that talks the record in, said last
  legal_id     text,                      -- said dry before the bed comes in; top-of-hour breaks only
  why          text not null,             -- the writer's one line: why this treatment here
  fallback     jsonb,                     -- {from, to, reason} when the clock rules stepped the kind down
  record_under_ms integer,                -- breaks: how far before the voice ends the record starts under it (the writer's number, clamped)
  voice_in_ms  integer,                   -- talkups: how far into the record the voice comes in (the writer's number, clamped)

  -- the voice half, landed by the audio rung
  clip_key     text,                      -- bucket key of the clip; written only after the PUT succeeded
  voiced_at    timestamptz,               -- set ⇒ done, nothing more will ever happen to this slot

  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now(),
  unique (segment_id, seq)
);

Two halves, two writers

The split matters because the two halves have different producers, different failure modes, and different immutability:

HalfWritten byWhenMutability
kind, words, lead_line, legal_id, why, fallback, record_under_ms, voice_in_msthe program rung — one Claude call, all slots in one transactiononce, after the playlistimmutable once written
clip_key, voiced_atthe audio rung — ElevenLabs plain TTS, per slotper slot, in any order the client asks (in practice: in order)immutable once voiced_at is set

Timing is opportunistic, not measured. The writer gives two numbers with the words — how far before the voice ends a break's record starts under the lead line, how far into the record a talk-up's voice comes in — kept where they mean something and clamped to sense. Everything else about the mix is a house constant in the player (plan.ts next to the session page): the bed under the break from the start (after a dry legal ID), its ramps, a talk-up done a beat before the card's intro ends, a sweeper dry then a hard start. The clip's length is read by the browser when it loads the clip. No alignment, no timestamps, no ladder. The clip bytes go to the bucket at sessions/<sessionId>/<num>/<seq>.mp3, immutable; the row holds words, the two numbers and the key. A failed TTS is a 502 the client may retry; a slot never fails silently.

Readiness

The audio rung PUTs the clip to the bucket first, then updates the row (clip_key, voiced_at) in one statement. So clip_key present always means the media exists. clip_key alone isn't enough to mean "done" because a segue finishes with no media — that's what voiced_at is for:

voiced_atclip_keyMeaning
nullnullnot voiced yet
setsetdone, media in the bucket — stream the GET endpoint
setnulldone, no media (segue or fallback) — just play the record
nullsetimpossible given the write order

A segment is playable once slot 1 has voiced_at (the break exists); fully voiced when every slot does. A crash between PUT and update leaves an unreferenced mp3 in the bucket; the retried rung overwrites it.

Why rows, not a jsonb array on the segment. The old world grew four parallel arrays on the segment row one item at a time (lines, log.slots, elements, notes) — that parallel-array bookkeeping is a good part of what made it spaghetti. Rows give each slot its own voiced_at instead of "array length = progress", make the audio rung's idempotency a one-row check, and let the two halves land as plain column updates under the session lock.

The four kinds

The clock rules live beside the program rung in apps/web/src/app/api/sessions/rules.ts, table-tested.

4. card — carried over in schema

The record's card (db/schema/card.sql) survives the refactor as-is: intro length, sure, the post (where the vocal comes in, never the lyric), ending, energy, talking points — keyed by Spotify track id, shared by every session, the first session to play a record pays for its card. The program rung reads cards to know which tracks can carry a talk-up (a talk-up needs a ≥ 7 s intro); the snapshot joins each slot's introMs from its card so the player can end a talk-up a beat before the vocal. Cards may be corrected in place; voiced slots never re-read them.

6. The old world next door

station and segment (the skeleton, the four parallel arrays) are the previous design, still in the schema and still behind the old routes. Nothing in the sessions world reads them. They — and the session_ prefixes here — go away when the old routes are deleted.
